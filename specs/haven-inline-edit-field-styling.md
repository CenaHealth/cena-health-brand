# Haven inline-edit field styling — the per-row commit field family

_Brand-spec for the `field-row-inline-edit` primitive that pairs a read-only key/value display with a hover-revealed Edit affordance, an editing-mode input, adjacent Save + Cancel, and a brief saved-flash success treatment. Visual treatment + rationale only; structure and CSS implementation live in [`Lab/haven-ui/packages/design-system/pattern-library/components/form-inline-edit.html`](../../haven-ui/packages/design-system/pattern-library/components/form-inline-edit.html) and [`packages/design-system/src/styles/tokens/components.css`](../../haven-ui/packages/design-system/src/styles/tokens/components.css)._

---

## 1. Context

The `field-row-inline-edit` primitive is a variant of haven's `field-row` family — it pairs the existing label register with a read-mode value display, a hover-revealed Edit affordance, and an editing-mode input + Save + Cancel cluster. The variant earned codification when the cena-apps internal-app Kitchen detail wireframe (cap-63 D2.1) called for per-row commits of contact-info fields (name, contact name, contact email, contact phone, login email) so the operator can land a single contact change without saving the whole card. The same call-out re-surfaced on the Programs-edit form (cap-59) for high-frequency-change fields (markup %, delivery fee). Per `generative-determinism.md`'s shape trigger and `haven-primitive-codification.md`'s codify-at-creation rule, the primitive lands pre-emptively rather than letting two consumer surfaces re-derive the same composition.

**Why a separate variant vs. `field-row-derived-override`.** Both variants share the data-state attribute pattern and the adjacent-Save commit contract, but they answer different brand questions. `field-row-derived-override` is "this field has a derived default; you can override it" — the derived rationale is load-bearing in the read register. `field-row-inline-edit` is "this field has a value; you can edit one row at a time" — the value itself is the read register, and the Edit affordance is the entry point to a single-row edit. The two variants compose alongside `field-row-default` and `field-row-prefix` in the same card without competing.

**Brand intent.** The variant must read as **"this row's value is editable, but quietly"** at a glance. The read register should dominate; the Edit affordance should reveal on intent (hover or focus) without competing for attention in a column of editable rows. Every visual decision below serves that one read.

---

## 2. Brand frame for this variant

The variant sits inside haven's existing `field-row` family. A reader scanning a kitchen-info card containing 5 inline-edit rows should see "a list of value-pair rows, each editable" — not "a list of edit-mode forms" and not "a list of read-only rows with hidden actions." Three brand decisions follow from that constraint:

- **The Edit affordance is hover-revealed and sand-neutral.** The affordance MUST exist (the operator needs to know the row is editable) but MUST NOT shout (a column of 5 sand-neutral always-visible edit buttons reads as a button-group, not a form). Reveal-on-hover/focus is the brand's answer: the affordance is discoverable through interaction intent (hover with a pointer, focus-within with a keyboard), invisible at the row's resting state. The 28×28px sand-600 button (same weight as `.field-input-reset` from the derived-override family) reads as in-row chrome rather than a primary action. This is the load-bearing decision: pulling the Edit affordance to teal or to always-visible would let it compete with the Save button when the row enters editing mode, and would let a column of 5 rows read as 5 affordances instead of 5 read values.

- **The editing-mode transition replaces the read-row's value display.** When the row enters `editing`, the value-row hides and the input + Save + Cancel cluster takes its place. The row's vertical rhythm shifts (it gets slightly taller to accommodate the input + adjacent actions) but the row's left-edge label register stays anchored, so the row reads as "the same row, in edit mode" rather than as a new component. A reader scanning a card with 1 editing-mode row and 4 read-mode rows should see "one row is being edited" not "the form has changed."

- **Save is `btn-primary` teal; Cancel is `btn-outline` sand.** Save IS a state-changing commit (the row's value changes on success). Cena reserves teal for state-changing commits per `DESIGN.md §Brand-taste`, and Save earns the teal moment for the row. Cancel is the dismiss-without-commit affordance; `btn-outline` (sand-200 ring, sand-700 text) gives it equal information weight without claiming commit semantics. The two buttons sit adjacent to the input — Save first (rightmost commit slot per family convention), Cancel after — so the reading order matches the operator's mental model: input → commit.

The "grew, not built" test on this variant: a kitchen-info card containing 5 `field-row-inline-edit` rows in read state should read as a single coherent form of editable values. If any row's Edit affordance is always-visible (over-revealing), the row visually competes with its siblings. If the editing-mode transition pulls the row out of vertical rhythm, the form reads as broken. If Save and Cancel sit on different visual planes (one inline, one in a footer), the commit contract feels confused.

## 3. States — visual treatment + rationale

The row carries `data-state="read|editing|saving|saved|error"`. The CSS family handles the visual transitions between states; the consumer's renderer is responsible for setting `data-state` based on row commit lifecycle.

### 3.1 Read state — value visible; Edit affordance reveals on hover/focus

- **Semantic intent.** No edit in progress. The row displays the current value alongside the label. The Edit affordance is present in the DOM but visually hidden until the operator hovers or keyboard-focuses into the row.
- **Visual treatment.** Label renders at the family's `field-label` register (sand-700 text-sm medium). Value renders at `text-sm text-sand-800` (matches form-input read weight). Edit affordance: 28×28px button, `fa-pen` glyph (FA Pro canonical edit affordance — chosen over `fa-pencil` for the bolder weight at small sizes that holds up at 12px icon size), sand-600 idle, sand-100 hover ground, sand-700 hover text. `opacity-0` at the row's resting state; `opacity-100` on row-level `:hover` or `:focus-within`, or on the button's own `:focus-visible`. Dark mode: sand-300 idle, sand-700 hover ground.
- **Rationale.** The hover-reveal pattern is the variant's load-bearing brand decision. Always-visible Edit affordances on a column of inline-edit rows let the column read as a button group; hidden-until-hover affordances let the column read as a value column with editability *available* on intent. The keyboard-equivalent (`:focus-within` on the row + `:focus-visible` on the button) is required so the affordance is discoverable without a pointer. The pen-glyph choice (`fa-pen` vs. `fa-pencil`) is brand-intentional: pen is the bolder, more affordance-shaped glyph at small sizes; pencil reads as a draft/sketch metaphor that the variant does not want to invoke (the operator is editing a committed value, not sketching a draft). The sand-600 weight matches `.field-input-reset` exactly — one in-row affordance vocabulary across the family.
- **Quality-test notes.** Quiet-mode: a kitchen-info card with 5 rows in read state reads as a column of label/value pairs with no visible affordances until the operator interacts. Hovering a row reveals a single sand-neutral pen icon; tabbing through reveals each one in turn. Grew-not-built: the affordance shares glyph weight and sizing with `.field-input-reset` (same in-row affordance register) so the family reads as one vocabulary.

### 3.2 Editing state — input + adjacent Save + Cancel; read-value hidden

- **Semantic intent.** The operator clicked Edit. The row's read-value display hides; the input + adjacent Save + Cancel cluster takes its place. The input is pre-populated with the current value, focused, and ready for typing.
- **Visual treatment.** Value-row hidden. Input-wrap visible: input renders at the family's `form-input` weight (sand-200 border, sand-50 background, sand-800 text), takes the available width. Adjacent action group: Save composes `btn-primary` (teal-700 fill, white text), Cancel composes `btn-outline` (sand-200 ring, sand-700 text), both at the row's default footprint. Action group sits to the right of the input at sm+ breakpoints; stacks below at mobile widths. Dark mode: input border sand-700, background sand-800; Save inherits btn-primary dark treatment; Cancel inherits btn-outline dark treatment.
- **Rationale.** The editing state is where the variant earns its codification — three things change simultaneously (value hides, input appears, action cluster appears) and the row's visual hierarchy reorients around the pending commit. Hiding the read-value (rather than dimming it or pushing it to a secondary position) is the key brand decision: the operator is now telling the system "ignore the old value, here's the new one," and the old value would compete for attention if it remained visible. Save and Cancel sitting adjacent to the input (sibling, not nested) preserves the row's left-edge label rhythm with other field-rows in the same card — the input-group's left edge aligns with sibling rows' left edges; the action cluster's right edge aligns with the card's right edge or with whatever right-anchor the surrounding form uses. The decision to put Save before Cancel (left-to-right in the action group) is brand-intentional: the commit is the primary affordance, and the leftward position matches the input's adjacency (the operator's eye moves: input → Save), with Cancel as the secondary escape hatch.
- **Quality-test notes.** Quiet-mode: the only teal moment on the row is the Save button. The Cancel stays sand-neutral; the input border stays sand-200 (no commit-pending border treatment); the label stays sand-700. Grew-not-built: the Save+Cancel cluster reads as "the row's commit pair, sized for the row's context," not as a footer-form's commit pair elevated above the field. Touch target: Save and Cancel inherit btn-primary/btn-outline footprints (44×44 minimum per accessibility floor).

### 3.3 Saving state — input + buttons disabled; Save renders spinner

- **Semantic intent.** Save was clicked; the request is in flight. Input + Cancel disabled (operator can't change their mind mid-flight without explicit cancel-mid-save UX); Save shows a spinner in place of its label text.
- **Visual treatment.** Input: `disabled` attribute, opacity-60, cursor-not-allowed. Cancel: `disabled` attribute, opacity-60 (inherits btn-outline disabled treatment). Save: `disabled` + `aria-disabled="true"`, opacity-60, spinner glyph (`fa-spinner-third` with `fa-spin` animation) replaces the "Save" text. The spinner has `aria-hidden="true"`; an `sr-only` "Saving" label provides screen-reader context. Dark mode mirrors with opacity-60 across the trio.
- **Rationale.** The saving state is short-lived (typically <1s for a single-field write), but it MUST be visually distinct so the operator knows the commit is in flight rather than wondering whether the click registered. Replacing Save's label text with a spinner (rather than adding a spinner alongside the label, or showing a separate loading bar) keeps the row's vertical rhythm intact — the button's footprint stays the same, the only change is the inner glyph. Disabling both the input and Cancel during saving prevents two failure modes: (a) the operator types a new value mid-save and gets confused which value committed, (b) the operator clicks Cancel mid-save and the row enters an ambiguous "did the cancel land or did the save land first" state. Cancel-mid-save UX is real but out of scope for V0; future surfaces can wire a "Cancel save in progress" affordance that dispatches an abort signal. The `aria-disabled="true"` on Save (rather than just `disabled`) is brand-intentional: the button is *busy*, not *invalid*, so screen readers announce "Saving, button" rather than "Save, dimmed button."
- **Quality-test notes.** Quiet-mode: the row reads as "edit-in-progress, please wait" with a single small teal spinner inside the Save button. Grew-not-built: the disabled treatment matches the form family's existing disabled state (opacity-60 + cursor-not-allowed); the spinner is the same `fa-spinner-third fa-spin` haven uses elsewhere for in-flight states. Reduced-motion: when `prefers-reduced-motion: reduce` is set, the spinner glyph is replaced with a static `fa-circle-notch` (no animation) via consumer composition; the variant's CSS does not override `fa-spin` because the glyph is the consumer's compose-time choice.

### 3.4 Saved state — brief success flash; returns to read with new value

- **Semantic intent.** The save committed successfully. The row's value-row reappears with the new value; a brief success flash (border + background) plays for ~1200ms then fades; the row returns to its read register.
- **Visual treatment.** Value-row visible (same as read state). Compose `.field-inline-edit-flash` on the value-row: CSS animation `inline-edit-flash 1.2s ease-out forwards` — at 0% the value-row carries `background-color: success-50` + `box-shadow: 0 0 0 2px success-500`; at 100% both transition to transparent. The animation runs once and ends at transparent, leaving the row visually identical to a read row. An `aria-live="polite"` sr-only span on the row announces "Saved" (debounced 400ms by the JS module). Renderer holds `data-state="saved"` for ~1500ms (slightly longer than the animation so the flash completes before the state transitions), then transitions back to `read`.
- **Rationale.** The saved-flash is the variant's most-visible success affordance, and it earns its codification because operators committing per-row edits need a clear "yes, that landed" signal. Using a border + background flash (rather than a toast, a status-line, or a separate "Saved" badge) keeps the success acknowledgment scoped to the row — the operator sees the row they just edited flash, not a global toast they have to associate with the row. Choosing success-500 + success-50 (the family's existing success-state pair) rather than a teal-on-teal flash protects haven's "teal is for commits, success-green is for successful commits" register — the row had a teal moment during editing/saving (the Save button), and now it has a green moment for the successful outcome. The 1.2s ease-out duration is brand-intentional: long enough for the operator to perceive the flash and associate it with their commit, short enough that a column of multiple successive saves doesn't accumulate visual debris. The animation ends at transparent (rather than the success-color holding) because the row should return to its read register — a saved row is just a read row whose value happened to change. The reduced-motion treatment (animation-duration: 0.001s) collapses the flash to a no-op for operators with motion sensitivity; the success acknowledgment in that case is the aria-live announcement + the value-change itself, which are sufficient on their own.
- **Quality-test notes.** Quiet-mode: a single row flashing success-green for 1.2s is the column's only loud signal; sibling rows stay in their read register. Grew-not-built: the success-500 + success-50 pair matches `.field-row-success` family treatment so the family's success vocabulary reads as one register. The animation ends cleanly at transparent (no held color) so the column returns to its read-mode rhythm with no residue.

### 3.5 Error state — save failed; input preserves value; error message inline; Save + Cancel visible

- **Semantic intent.** Save was attempted and failed (server rejected, validation failed, network failed). The operator's value is preserved in the input so they can correct it; the error message renders inline below the input; Save remains available for retry; Cancel remains available for "give up and revert to the previous value."
- **Visual treatment.** Compose `field-row-inline-edit` + `field-row-error` (the existing family modifier). Input border turns red (`field-row-error input { border-color: error-500 }`), `aria-invalid="true"`, `aria-describedby` points at the error message. Error message renders below in `.field-error` register (text-sm text-error-600, leading `fa-circle-exclamation`). Save + Cancel visible (same treatment as editing). Dark mode: error uses `error-400` per the family's error treatment.
- **Rationale.** The error state composes two existing families (`field-row-inline-edit` + `field-row-error`) rather than introducing new chrome — protects the "grew, not built" test by letting the row inherit the family's existing error vocabulary. The error message renders below the input (rather than replacing the value-row entirely) because the input + Save + Cancel cluster is still the operative read — the operator needs to correct and retry, and the error message is supplementary context. Save staying visible is critical: errors are recoverable, and the operator needs to retry without leaving the row. Cancel staying visible is the operator's escape hatch — "this isn't working, revert to what was there before." The reader's mental model: "this is an editing row whose save failed; I can correct + retry, or cancel back to the previous value."
- **Quality-test notes.** Quiet-mode: the red border is the only loud signal; the error message reads in error-red but at the family's text-sm register; Save stays teal; Cancel stays sand-neutral. Grew-not-built: the error treatment matches `field-row-error` exactly so a future agent reading this state recognizes it as "haven's standard error state, applied to the inline-edit row."

## 4. Cross-cutting decisions

What this variant asserts about the brand, taken as a system:

- **Hover-revealed affordances are sand-neutral; they earn presence through interaction, not hue.** The Edit button reads as in-row chrome (sand-600 idle, sand-100 hover ground), matching `list-group-item-action` hover semantics, `quantity-stepper-btn` weight conventions, and `.field-input-reset` from the derived-override family. Pulling the Edit affordance to teal or to always-visible would let it compete with the row's Save button when editing, and would let a column of 5 rows read as 5 affordances instead of 5 read values.
- **Reveal-on-hover MUST be paired with reveal-on-keyboard-focus.** Pointer-only reveal is an accessibility floor failure. The `:focus-within` selector on the row + `:focus-visible` on the button ensure keyboard operators see the affordance when they tab into the row.
- **Editing-mode transition replaces (does not co-exist with) the read-mode value.** The value-row hides when editing begins. Co-existing read + input would let the row visually compete with itself.
- **Save is `btn-primary` teal; Cancel is `btn-outline` sand.** Save IS a state-changing commit; teal earns its place. Cancel is the dismiss-without-commit; sand-neutral keeps it from claiming commit semantics.
- **Saved-flash uses success-500 + success-50, not teal-on-teal.** Teal is for commits-in-progress (Save button); success-green is for commits-that-landed. The brand's success vocabulary owns the "yes, that worked" register.
- **Saving-state disables input + Cancel; Save shows a spinner.** Prevents mid-flight ambiguity. Cancel-mid-save UX is deferred (real but out of scope for V0).
- **The variant is NOT the derived-override pattern.** Derived-override has a derived default and a reset; inline-edit has only an editable value. Future surfaces composing these alongside each other should distinguish by intent: "this field has a derived default" → derived-override; "this field has an editable value" → inline-edit.
- **No new typography weights or sizes.** All slots use Source Sans 3 in the `text-sm` (label, value, input) / `text-xs` (error) register. Save inherits btn-primary's type contract; Cancel inherits btn-outline's. The variant does not earn a Lora moment — Lora is reserved for headings and the document district's authority register; form rows are working-voice.
- **State is bound via `data-state` on the row.** No state-specific CSS classes added to children; the row's `data-state` attribute drives child visibility. Protects the family from per-state class soup.

## 5. Open issues / future work

1. **Vanilla JS module ships in a follow-up slice.** Per the PL fragment's `@component-meta` notes, the state-binding + event-dispatch behavior (`inline-edit.js`) ships when the cena-apps internal-app lights up client-side state. V0 renders the markup with `data-state` set per-row by the renderer; the five PL exemplars (read / editing / saving / saved / error) are static composition examples. When the JS lands, the brand spec re-validates the live state transitions against the five static states above.

2. **Cancel-mid-save UX.** The saving state disables Cancel to prevent mid-flight ambiguity. Real-world surfaces with slow networks may want a "Cancel save in progress" affordance that dispatches an abort signal. Not authored speculatively; codify when a consumer surface needs it.

3. **Multi-field row variant.** The variant assumes one editable field per row. Future surfaces (e.g., a contact-info card where the operator wants to edit name + email together) may want a row-level edit mode that opens multiple inline inputs at once. Distinct shape from this variant; codify when a surface needs it.

4. **Edit-affordance reveal on touch.** Touch devices don't have a hover state. Renderer + consumer have two options: (a) always-visible Edit affordance on touch (compose with a media-query override), (b) tap-to-reveal-then-tap-to-edit (two-tap pattern). Default behavior in V0: the affordance is always-visible on touch surfaces via a CSS `@media (hover: none)` override; codify the override in a follow-on slice when a touch-first consumer surface emerges. Not authored in V0 because the canonical consumers (Kitchen detail, Programs edit) are desktop-first staff surfaces.

5. **Compact-density saving spinner.** In tight density rows (table cells, compact lists), the saving spinner inside Save may be visually constrained. Default behavior is acceptable for V0 (Kitchen info card + Programs edit are not table-cell consumers). If a table-cell consumer composes this variant, the saving-state spinner may want a smaller glyph or a different presentation.

6. **Composing inline-edit alongside derived-override in the same card.** A future Kitchen detail composition could have inline-edit on contact-info fields and derived-override on meals-catalog override prices in the same card surface. Both compose the same `field-row` shell so the family's vertical rhythm is preserved, but the two variants' affordance-reveal patterns differ (inline-edit hover-reveals on hover/focus; derived-override always-shows the input). Document the composition pattern in the consumer's wireframe; no variant work needed.

## 6. Validation checklist (for the codification slice's render-pipeline verification)

After the variant ships in `components.css` + `form-inline-edit.html` and the cena-apps internal-app Kitchen detail Kitchen info card renders:

- [ ] Kitchen info card: each editable field composes `field-row-inline-edit` with `data-state` set per row's commit status
- [ ] Read state: label + value visible; Edit affordance hidden at rest; reveals on row-hover or keyboard focus-within; pen icon at sand-600 with `fa-pen` glyph; 28×28px footprint
- [ ] Editing state: value-row hidden; input visible with current value pre-populated; Save (`btn-primary` teal) + Cancel (`btn-outline` sand) adjacent
- [ ] Saving state: input + Cancel disabled (opacity-60, cursor-not-allowed); Save shows `fa-spinner-third fa-spin` glyph in place of "Save" text; `aria-disabled="true"` on Save; sr-only "Saving" label
- [ ] Saved state: value-row visible with new value; `.field-inline-edit-flash` animation runs over 1.2s (success-50 background + success-500 ring → transparent); aria-live announces "Saved"; row transitions back to read after ~1500ms
- [ ] Error state: composes `field-row-error` + `field-row-inline-edit`; input border red (`error-500`); error message visible below at text-sm error-600 with leading `fa-circle-exclamation`; Save + Cancel still visible
- [ ] Quiet-mode check: a column of 5 rows in read state shows no visible affordances at rest; hovering one row reveals exactly one pen icon; the column reads as a value-pair list, not a button group
- [ ] Grew-not-built check: composing one `field-row-inline-edit` alongside three `field-row-default` rows in the same card reads as a single coherent form; the inline-edit row doesn't visually compete for attention at rest
- [ ] Keyboard-focus reveal: tabbing through a column of read-state rows surfaces each Edit affordance in turn; enter/space on the affordance transitions to editing
- [ ] Reduced-motion: `prefers-reduced-motion: reduce` collapses the saved-flash to a 0.001s no-op; the success acknowledgment in that case is the aria-live announcement + the visible value change
- [ ] No row composition violates §4's cross-cutting decisions (no always-visible Edit affordance, no teal on Cancel, no Lora on labels, no per-state class proliferation)
- [ ] Save dispatches `inline-edit-save` CustomEvent with `detail.value`; Cancel dispatches `inline-edit-cancel`; Edit dispatches `inline-edit-enter` (when JS module lands; pre-JS V0 the static markup is the verification target)
